# Architectural review: platform primitives and E01-S01

Original review verdict: **revise before implementation**. The accepted product direction is workable, but the two specs contained incompatible contracts and incomplete concurrency rules. The platform catalogue is not itself a reason to reject the design; the unnecessary complexity came from making future mechanisms mandatory for the first account story.

**Resolution, 2026-10-31:** the user authorized applying these recommendations. All 12 findings below are addressed in the source specifications; they remain here as the original review record, with pre-edit line references. A follow-up consistency review found no remaining major cross-document scope/phasing conflict. This resolves the design findings, not their future implementation or runtime verification.

| Finding | Applied resolution |
|---|---|
| 1 | Explicit linking requires the same normalized primary verified email. |
| 2 | Linking/takeover lock the same user; signed link state carries the verified session version, rechecked under lock. Password login also rechecks its verified hash/version snapshot. |
| 3 | Separate local/provider redirect contracts; shared execution with distinct JSON/browser response adapters and error-cookie clearing. |
| 4 | One outer transaction owner; transaction-local pending events dispatched after its actual commit, introduced only with PP6. |
| 5 | Distinct duplicate/obsolete/retryable outcomes, atomic local deduplication and consumer-owned reconciliation. |
| 6 | Atomic attempt admission via `consume` only; no failure-only check/hit race or refunds. |
| 7 | Indexed expiry and globally bounded cleanup, with IP-first admission before email-key creation. |
| 8 | Accurate credential/data loss and backup/forward-repair recovery limits. |
| 9 | Explicit application of the existing compatibility policy and session invalidation requirements. |
| 10 | Pathname-only request logging and allowlisted OAuth error metadata, with secret-absence assertions. |
| 11 | Only auth-consumed helpers/errors in PP1; event integration deferred to PP6. |
| 12 | Reconciled OAuth summaries, role gates, page shells, password limits and internal release checkpoints. |

The simplification recommendations are also applied: lifecycle concurrency controls follow actual invariants; role-only policy wrappers are removed; read-triggered payout mutations are excluded; payment idempotency is explicitly separate from status transitions. Validation: `git diff --check` passed; no application tests were run for these specification-only edits.

Reviewed 2026-10-31. Source line numbers refer to the unchanged specifications. P = [platform primitives](../specs/2026-10-31-platform-primitives.md); A = [accounts and role access](../specs/2026-10-31-e01-s01-accounts-and-role-access.md).

## Findings

1. **High — linking bypasses the proposed defence against email squatting.** A:24–30, 168–179. An attacker registers a victim's email, then links the attacker's GitHub identity whose verified email differs. `linkGitHub` permits this and leaves `emailVerifiedAt` null. The victim subsequently signs in with their own GitHub identity: Q12 no longer applies because `githubId` is set, and the victim receives `github_account_exists`. This is account squatting/denial of access, not proof that the attacker can enter an already verified victim account. **Correction:** define which email the linked account may retain. Require proof of the claimed account email before keeping it alongside a different GitHub identity, or explicitly design recovery for linked-but-unverified email claims. Test this exact sequence. The approved absence of verification emails does not resolve this contradiction.

2. **High — takeover and linking need a shared concurrency rule.** A:173, 177–180, 325. Q12 specifies a transaction, but does not require locking or a conditional update of the unlinked/unverified predicate. An existing password session can begin `linkGitHub` while the verified email owner begins takeover. Both can read the old state; the last write can replace the other identity. Checking the session only at request entry also does not prevent a link already in flight from writing after `session_version` is revoked. A unique `github_id` prevents one identity appearing on two rows; it does not prevent two identities overwriting one row. **Correction:** serialize both operations on the user or use conditional updates, recheck current identity/session version inside the mutation, and add a concurrent link-versus-takeover integration test. Keep the check and write in the same protected operation.

3. **High — the redirect contract cannot express GitHub sign-in.** P:128–138 makes `redirectTo(SafePath)` the only redirect mechanism, with local-path validation. A:47 and 147 require a redirect to GitHub's external authorization URL. These requirements cannot both be implemented as written. **Correction:** retain local-only validation for user-provided `next`, and define a distinct trusted provider redirect result constructed from configured OAuth endpoints. Do not widen `SafePath` to arbitrary URLs. Also specify browser-route error handling before `apiHandler` converts exceptions to JSON: the existing handler always envelopes results/errors (`packages/core/src/http/api-handler.ts:28–50`). A shared execution function with JSON/browser response adapters is sufficient; two nested error pipelines are unnecessary.

4. **High — webhook and service contracts disagree about who commits.** P:266, 274–275, 283. Services must open transactions and commit before returning; the webhook wrapper must insert its inbox row and run those services in one enclosing transaction. A service cannot guarantee the enclosing commit when it returns. Separately, a route can commit service A, fail in service B, and discard all recorded events despite A having committed. **Correction:** choose one owner of the outer transaction for a workflow, join it from participating services, and tie event collection/discard to that transaction. Dispatch after the actual outer commit. Explicitly limit these best-effort events to noncritical effects; this does not require introducing a queue. Tests should cover rollback after a recorded event and failure after an earlier independent commit.

5. **High — blanket acknowledgement of invalid webhook transitions loses legitimate work.** P:283 and 387. The spec groups replay and out-of-order delivery together, then acknowledges every invalid transition with 200. A transition temporarily invalid because its prerequisite has not arrived is different from a duplicate or permanently irrelevant event. Acknowledging it without reconciliation leaves no specified way to apply it later. **Correction:** distinguish duplicate, terminally obsolete, temporarily out-of-order, and failed processing. For temporary ordering gaps, reconcile authoritative state or retain retryable work; mark an inbox event processed only when the chosen outcome is durable. Describe the guarantee as atomic deduplication of local database effects, not universal exactly-once execution of external side effects.

6. **High — login limiting is a check-then-act race.** P:215, 218–221; A:156. Atomic `consume` does not protect the separate `check → password verification → hit` path. Many simultaneous requests can all pass `check` before any failure increments the counter, admitting a batch of guesses far above the stated limit. **Correction:** atomically reserve an attempt before expensive verification, or add an atomic attempt cap alongside the failure policy. If successful attempts are refunded, define concurrency-safe refund semantics. Test simultaneous failing logins, not only concurrent bucket upserts. The accepted per-email lockout trade-off is a separate issue.

7. **Medium — rate-limit cleanup leaves abandoned keys forever.** P:216, 225; A:157. Cleanup runs only when the same key is used again. Registration with fresh email addresses therefore creates persistent rows that will never be revisited. Hashing addresses does not bound cardinality. **Correction:** define bounded deletion of globally expired buckets, triggered opportunistically or by an existing maintenance command, and an expiry index. No new worker framework is needed.

8. **Medium — rollback is described as losing only roles, but removes credentials too.** A:108–114, 252. Dropping the new columns also removes password hashes, GitHub associations, verification timestamps and session versions. `operator:grant` cannot reconstruct these, and itself requires a linked account. **Correction:** document the actual destructive consequences and a backup/restore or forward-repair procedure. Do not present this as a recoverable role-only rollback.

9. **Medium — compatibility analysis relies on a false repository premise.** P:143, 393 claims there is no `BACKWARD_COMPATIBILITY.md` and calls the API change nonbreaking because there is one consumer. The file exists. Its sections 4–5 explicitly classify session-claim changes and exported symbol/signature replacements as breaking, with manageable migration requirements. **Correction:** cite the policy, update every internal caller in the same PR, state session invalidation, and retain the required risk classification and second review. A private monorepo permits coordinated migration; it does not erase the contract change.

10. **Medium — OAuth redaction omits the actual request-log shape.** P:364; A:85, 228. Redacting `query.code` and `body.code` does not sanitize a code embedded inside the string `url`. The reused error pipeline currently logs `request.url` (`packages/core/src/http/api-handler.ts:49`). **Correction:** require OAuth-safe URL logging (for example pathname only), and test an unexpected callback error to assert the authorization code, state and tokens are absent. This is a design gap in the proposed reuse, not a claim that a future browser wrapper already leaks them.

11. **Medium — implementation timing contradicts the first-consumer rule.** P:141 requires event dispatch in `apiRoute` immediately, but P10 ships only in PP6 (419). PP1 step 1 (428) adds all errors, including settings, transition and edit-conflict errors; step 4 (436) adds `isParty`, whose consumers are later booking/session/note stories. This conflicts with P:409 and the repository's YAGNI rule. **Correction:** build only auth errors/predicates now, and explicitly add event integration when P10 ships. Retain the later contracts as proposals to be ratified with their consumers. Do not introduce placeholder services merely to make a future-oriented diagram compile.

12. **Low — stale summaries and phase labels leave competing versions of the design.** A:53 says matching email is refused without the Q12 branch; A:139 says every route returns an envelope although OAuth returns redirects; A:92 mentions layout navigation despite P:186–189 putting shells in pages. A:265 calls Phase 2 independently shippable, while A:247 says operator bootstrap depends on Phase 3 and the story releases together. **Correction:** reconcile summaries with the normative contracts and call phases internal checkpoints unless a usable independent release/bootstrap path is supplied. Also align the password table's “12–72 bytes” (A:143) with the stated minimum of 12 characters and maximum of 72 bytes (154).

## Simplification priorities

- Keep the two-spec split, fixed role set, database-resolved actor and existing four packages. These are accepted decisions, not findings.
- Implement a thin shared request execution path and explicit JSON/browser response adapters. Keep webhook transaction handling with the payment consumer instead of building it into auth now.
- Scope P9's universal lifecycle/version rule to demonstrated requirements. A transition map checks legal status changes; it does not establish business idempotency. P:269 and 329 should not imply that reaching the same status proves an external payout happened once. The payment story must specify that boundary.
- Avoid both `{ anyRole: ["operator"] }` and separate role-only policy wrappers as independently maintained definitions. Reuse a predicate where it adds a shared rule; keep record-level ownership in services.
- Treat P12–P17 sketches as nonbinding. In particular, do not let a speculative audit system or polymorphic token framework delay S01. A small typed helper can be appropriate once a concrete consumer exists.

## Review limits

Compared both specifications in full with repository instructions, engineering standards, relevant product-brief rules, compatibility policy, lessons and existing HTTP/auth/container/form code. Independent reviewers checked scope cohesion and authentication contracts. No source code or source specification was changed. No implementation tests, live OAuth/provider verification, browser session or external tracker review was performed; this is a design review, not runtime validation. Findings about concurrency describe executions permitted by the written contracts and require regression tests during implementation.
