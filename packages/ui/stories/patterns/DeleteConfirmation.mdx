# Delete confirmation

Use this pattern before an irreversible loss of money or data. DevMentor's concrete example is a mentee cancelling a paid booking: the payment is not refunded. This is a cancellation, not deletion of the session history. (Brief R27/D39; WCAG 3.3.4.)

The asynchronous composition and copy are **proposals pending E03-S03**. The story simulates a result boundary; it does not define an endpoint, idempotency policy, cancellation eligibility or payment transition. Those belong to the covering specification and server. (Design-system spec, accepted E02–E05 proposal policy; engineering standards, API and authorization layers.)

## Compose the confirmation

Use `AlertDialog`, its title, description, footer, cancel and action exports from `@devmentor/ui/components/ui/alert-dialog`. Use `Button` for the trigger and `ErrorMessage` from `@devmentor/ui/backend/feedback` for a request failure. The title names the object, person and time; the description states the financial consequence. Never use “OK” as the action label. (Task stage 3; brief R27; WCAG 3.3.4; WAI-ARIA APG Alert Dialog.)

<Canvas of={Confirmation.Confirmation} />

Keep the safe “Zostaw rezerwację” choice easy to find and initially focused. Tab stays inside the modal; Escape closes it before a request starts and returns focus to the trigger. Clicking the scrim does not confirm. Both choices inherit the package's focus and target-size styles. (WAI-ARIA APG Alert Dialog; WCAG 2.4.3, 2.4.7, 2.5.8.)

## State map

| State | Story | Behaviour and source |
| --- | --- | --- |
| Confirmation | Confirmation | Name the object and no-refund consequence before the destructive action (R27; WCAG 3.3.4) |
| Safe exit | SafeCancelAndFocusReturn | Escape closes without requesting cancellation and restores trigger focus (WAI-ARIA APG) |
| Awaiting response | WaitingForServer | Keep the dialog open, show a live status and explain temporarily disabled actions; never announce success yet (proposal; WCAG 4.1.3) |
| Request failed | ServerError | Keep the context and actionable error visible; ask the user to verify state before retrying (proposal; WCAG 3.3.1) |
| Server confirmed | ServerConfirmedSuccess | Close only after simulated success; announce the confirmed outcome and financial consequence (proposal; R27; WCAG 4.1.3) |
| Narrow screen | NarrowConfirmation | Title and consequence wrap inside token-based dialog margins (WCAG 1.4.10; approved dialog tokens) |

## Wire the server boundary

Prevent the default immediate close of `AlertDialogAction` while submitting. Keep the root controlled and update the visible result only after the application's `apiCall` response. Block duplicate requests while waiting; a UI lock does not replace server authorization or idempotency. (Engineering standards, reusable API layer and fail-closed authorization; task stage 3 form behaviour.)

<Source language="tsx" code={`import { AlertDialogAction } from "@devmentor/ui/components/ui/alert-dialog";

<AlertDialogAction
  variant="destructive"
  disabled={pending}
  onClick={(event) => {
    event.preventDefault();
    void requestCancellation();
  }}
>
  {pending ? "Anulowanie…" : "Anuluj rezerwację"}
</AlertDialogAction>`} />

The example holds the modal open during a pending request and explains that cancellation is unconfirmed. A production timeout, safe recovery and navigation policy still need an E03-S03 decision; do not copy an indefinite wait into the application. A network failure does not prove the server rejected the operation. (Proposal; missing E03-S03 contract.)

## Review at each width and theme

At 320 px check wrapped title and stacked actions; at 768 and 1440 px keep the same bounded dialog rather than enlarging it to the page. Inspect both themes on the document root so the portalled surface, scrim and focus ring use the correct tokens. Read the full consequence before pressing Enter. (Task stages 1–3; WAI-ARIA APG; WCAG 1.4.10, 2.4.7.)

Do not replace the confirmation with a toast, remove the object's name, show optimistic cancellation success or promise a refund. For a reversible local edit use an ordinary action; for multi-step account removal use a dedicated specified flow instead of extending this example. (R27; task stage 3; final routing sentence is a proposal.)
