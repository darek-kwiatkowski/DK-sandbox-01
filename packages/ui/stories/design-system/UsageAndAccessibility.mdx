# Usage and accessibility

These are implementation rules, not optional polish. Cite the source when a screen documents a product rule; unresolved behavior must remain a visible gap. (Approved design-system brief; WCAG 2.2.)

## Keyboard and focus

- Use native links for navigation and buttons for actions. All controls must work from the keyboard; preserve the browser's expected Enter, Space, arrow-key and Escape behavior. (WCAG 2.1.1, 4.1.2; WAI-ARIA Authoring Practices Guide.)
- Keep focus visible and in a logical order. Dialogs and alert dialogs must move focus into the overlay, keep it there while modal, close with Escape when allowed, then return focus to the trigger. (WCAG 2.4.3, 2.4.7; WAI-ARIA Dialog and Alert Dialog Patterns.)
- Interactive targets must be at least 24 × 24 CSS pixels or meet WCAG 2.5.8's spacing exception. (WCAG 2.5.8.)
- A tooltip must open from keyboard focus as well as pointer hover, remain dismissible and must not contain the only copy of an instruction. (WCAG 1.4.13; approved G2; WAI-ARIA Tooltip Pattern.)

## Forms and feedback

- Keep the label visible; a placeholder is an example, never the field name. Identify required/optional status and connect instructions and field errors programmatically. (WCAG 3.3.2, 1.3.1; P18.)
- Validate on blur and submit. On failed submit, focus the first invalid field, preserve entered values and associate each error with its field. Do not submit twice while a request is pending. (Approved stage-3 form requirements; WCAG 3.3.1, 3.3.3.)
- Announce loading and asynchronous results with the appropriate status or alert semantics. Declare success only after server confirmation. An action-required error remains visible until resolved. (WCAG 4.1.3; approved stage-3 form requirements.)
- Explain why a disabled action is unavailable next to that action. Do not rely on a disabled control or tooltip alone to convey the reason. (WCAG 3.3.2; R29.)

## Color, motion and content

- Use semantic tokens for color in both themes. Color never carries status alone; pair it with text, an icon or another visible cue. (Approved `tokeny.md`; WCAG 1.4.1.)
- Text contrast is at least 4.5:1 for normal text; UI component boundaries and focus indicators meet 3:1 where WCAG requires it. Check foreground/background pairs in both themes. (WCAG 1.4.3, 1.4.11; Color foundation.)
- Respect `prefers-reduced-motion`; decorative motion is not part of this system. Keep motion limited to state confirmation. (P18; approved Motion foundation; WCAG 2.3.3.)
- State prices and refund rules before payment; do not promise response speed or availability. Use the product's approved Polish UI copy in examples. (R14, R27, R33; P17; A06.)

## Layout and product rules

- Check reflow at 320 px, tablet layout at 768 px and wide layout at 1440 px. Long names, labels, URLs and translated copy must wrap without clipping or page-level horizontal scrolling. (Approved F1/F3; WCAG 1.4.10.)
- Keep long reading text near `max-w-reading`; use the page-width token for the overall page. Do not apply dense list spacing to session conversation or notes. (K1; R01.1, R02.1.)
- Give one item visual priority at a time. On a mentor list it is the next published slot; on a booking list it is the booking date/time; in an active session it is the time remaining. Use color or type weight, not both. (R01.5; K3.)
- Mentor discovery is stack-filtered and ordered by published availability, without ranking or ratings. (R13, N02.)
- One session is one linear text conversation. Every message shows its author and time; Enter sends and Shift+Enter inserts a line break. (R02.2, R02.3, R02.8; K4.)
- Mentee and mentor co-edit one private note; only the mentee approves the final note. Do not expose it publicly or claim local UI state as persisted approval. (R26, R31; E04-S02.)
- A slot starts at least two hours in the future, sessions last 25 or 50 minutes, and real payment requires approved terms and an operator-set fee. (R14, R28, R29, R33; D46.)
